## Phase Details

### Phase 115: Generic Constraints
**Goal**: Users can declare and have compiler-enforced contract bounds on generic type parameters
**Depends on**: Nothing (builds on existing parsed-but-unenforced FnSig.bounds infrastructure)
**Requirements**: GEN-01, GEN-02, GEN-03, GEN-04, GEN-05, GEN-06
**Success Criteria** (what must be TRUE):
  1. User can write `fn foo<T: Eq>(a: T, b: T)` and call it with a type that implements Eq without error
  2. User can write `<T: Eq + Ord>` multi-bound syntax and the compiler enforces both constraints independently
  3. When user calls a bound-constrained function with a type missing the required contract, the compiler emits a `ConstraintNotSatisfied` error naming the missing contract and pointing to both the call site and the bound declaration
  4. The compiled IL binary's GenericConstraint table (table 14) contains rows for every bound declared on generic params
  5. The constraint violation error includes a concrete fix suggestion: "consider adding `impl ContractName for TypeName`"
**Plans:** 2/2 plans complete
Plans:
- [x] 115-01-PLAN.md — Type checker bounds enforcement with multi-span diagnostics (GEN-01/02/03/05/06)
- [x] 115-02-PLAN.md — IL GenericConstraint table emission (GEN-04)

### Phase 116: Array Primitives, String Utilities & Host Value Construction
**Goal**: Users can call mutation methods on arrays, string utility methods, and host Rust code can construct type-validated Writ values
**Depends on**: Nothing (independent virtual module extension + compiler dot-call resolution + runtime API)
**Requirements**: STR-01, STR-02, STR-03, STR-04, STR-05, STR-06, HOST-01, HOST-02, HOST-03
**Success Criteria** (what must be TRUE):
  1. User can call `arr.add(x)`, `arr.remove_at(i)`, `arr.insert(i, x)`, `arr.contains(x)`, `arr.slice(r)` on any `T[]` value and the compiler resolves and emits them correctly
  2. User can call `s.split(sep)` and receive a `string[]` array of substrings
  3. User can call `s.trim()`, `s.starts_with(p)`, `s.ends_with(s)` and receive correct results including on non-ASCII input
  4. User can call `s.contains(sub)`, `s.replace(from, to)`, `s.to_upper()`, `s.to_lower()` with locale-independent, Unicode-safe results
  5. The `Hashable` builtin contract is registered in the virtual module and auto-implemented for `int`, `string`, `bool`, and `float` primitive types
  6. Host Rust code can construct a Writ struct/class value by type name with runtime validation of field count and field types against module metadata
  7. Host Rust code can construct values in immediate extern handlers (heap access provided in handler context)
  8. Runtime returns a clear error when host constructs a value with wrong field count or mismatched field types
**Plans:** 3/3 plans complete
Plans:
- [x] 116-01-PLAN.md — Array primitive compiler wiring + ArrayContains opcode (STR-01)
- [x] 116-02-PLAN.md — String utility opcodes + Hashable contract registration (STR-01..06)
- [ ] 116-03-PLAN.md — Host value construction API + ImmediateWithHeap handler (HOST-01..03)

### Phase 117: Collections (List, Map, Set)
**Goal**: Users can create, populate, and query List<T>, Map<K,V>, Set<T>, and HashMap<K,V> as first-class generic types
**Depends on**: Phase 115 (GEN enforcement needed for `T: Eq`, `K: Hashable` bounds), Phase 116 (array dot-call methods needed for List<T> internals)
**Requirements**: COLL-01, COLL-02, COLL-03, COLL-05, COLL-06
**Success Criteria** (what must be TRUE):
  1. User can write `let list = List<int>(); list.push(1); list.pop(); list.get(0); list.set(0, 5); list.len(); list.contains(1)` and all operations produce correct results
  2. User can write `let map = Map<string, int>(); map.set("a", 1); map.get("a"); map.contains_key("a"); map.remove("a"); map.keys(); map.values()` and get O(log n) sorted-array-backed behavior
  3. User can write `let set = Set<int>(); set.add(1); set.remove(1); set.contains(1); set.len()` and all operations produce correct results
  4. User can write `let hm = HashMap<string, int>(); hm.set("a", 1); hm.get("a")` with O(1) average lookup via the Hashable contract
  5. All four collection types are implemented in pure Writ source files, compiled as a library module loaded automatically before user code — no compiler special-casing
**Plans:** 3/3 plans complete
Plans:
- [x] 117-01-PLAN.md — Pre-work validation: GC struct-array tracing, generic inherent impl, library pre-load (COLL-06)
- [x] 117-02-PLAN.md — writ-std collection classes + golden IL snapshot tests (COLL-01/02/03/05/06)
- [x] 117-03-PLAN.md — CLI writ-std embedding + runtime integration tests (COLL-01/02/03/05/06)

### Phase 118: Iterator Protocol & Higher-Order Methods
**Goal**: Users can iterate over any collection with for-in syntax and chain map/filter/reduce on List<T>
**Depends on**: Phase 117 (List<T>/Map<K,V>/Set<T> must exist as concrete Iterable<T> implementors)
**Requirements**: COLL-04, ITER-01, ITER-02, ITER-03, ITER-04, ITER-05
**Success Criteria** (what must be TRUE):
  1. User can write `for x in list` and it iterates all elements via Iterable<T> contract desugaring (not a compiler built-in special case)
  2. User can write `for x in set` and `for k in map.keys()` and both work correctly via the same Iterable<T> path
  3. User can define a custom class that implements `Iterable<T>`, use it in a `for x in` loop, and the compiler compiles and runs it correctly
  4. `List<T>`, `Map<K,V>`, and `Set<T>` all implement `Iterable<T>` in their pure-Writ source definitions
  5. User can write `list.map(fn).filter(fn).reduce(fn)` chained calls on a `List<T>` and get a correctly accumulated result
**Plans:** 2/2 plans complete
Plans:
- [x] 118-01-PLAN.md — Writ-std iterator classes, Iterable impls, HOF methods, and golden tests (COLL-04, ITER-05)
- [x] 118-02-PLAN.md — Compiler for-in desugaring + integration tests (ITER-01, ITER-02, ITER-03, ITER-04)

### Phase 119: Diagnostics Polish & LSP Hardening
**Goal**: All v13.0 errors carry fix suggestions; the CLI can treat warnings as errors; the LSP remains usable during editing
**Depends on**: Phase 115 (constraint errors are the primary fix-suggestion target), Phase 118 (all new error sites present before quality pass)
**Requirements**: DIAG-01, DIAG-02, DIAG-03, DIAG-04
**Success Criteria** (what must be TRUE):
  1. A constraint violation error in the terminal shows two source spans: the call site and the bound declaration, with a secondary label explaining which contract is not satisfied
  2. Applicable compiler errors (constraint violations, missing impls) include a concrete fix suggestion rendered as a code snippet note in the terminal output and as an LSP `WorkspaceEdit` code action
  3. Running `writ compile --deny-warnings` on a file with deprecation warnings exits with a non-zero status and treats every warning as a hard error
  4. The LSP continues to provide completions and hover type information while the user is mid-edit with a syntax error in the file
**Plans:** 2/2 plans complete
Plans:

- [x] 119-02-PLAN.md — LSP partial-parse resilience verification + integration tests (DIAG-04)

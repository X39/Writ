# Requirements: Writ v14.0 Array Semantics & Cross-Module Resolution

**Defined:** 2026-03-29
**Core Value:** Correct, spec-compliant implementation at every layer — lowering matches Section 28 exactly, runtime matches the IL spec exactly — structured so each layer can be extended independently.

## v14.0 Requirements

### Array Semantics

- [x] **ARR-01**: `T[]` does NOT support `add`, `remove_at`, or `insert` — compiler rejects these as unknown methods
- [x] **ARR-02**: `T[]` supports `resize(new_len: int)` to reallocate the array to a new fixed size
- [x] **ARR-03**: `T[]` supports `copy(dst_idx, src, src_idx, len)` for bulk element transfer between arrays
- [x] **ARR-04**: `T[]` retains `len()`, `slice(start, end)`, and indexed access as the only other built-in operations
- [x] **ARR-05**: `contains` is removed from `T[]` (deferred to Iterable default impl in next milestone)
- [x] **ARR-06**: Language spec describes arrays as "fixed-size" with resize/copy as explicit operations; growth method docs removed

### Standard Library

- [x] **STD-01**: List<T> uses resize + indexed assignment internally (no removed array methods)
- [x] **STD-02**: Map<K,V> uses resize + indexed assignment internally
- [x] **STD-03**: Set<T> uses resize + indexed assignment internally
- [x] **STD-04**: HashMap<K,V> uses resize + indexed assignment internally
- [x] **STD-05**: All collection integration tests pass with rewritten internals

### Cross-Module Resolution

- [x] **XMOD-01**: Compiler can load type definitions from a pre-compiled `.writc` module into DefMap
- [x] **XMOD-02**: User code can reference types from a loaded library module and the compiler validates them at compile time
- [x] **XMOD-03**: Virtual module types (Type, FieldInfo, etc.) are resolvable through the same DefMap mechanism
- [x] **XMOD-04**: `coll_with_library_separate_modules` test passes (un-ignored)
- [x] **XMOD-05**: Language spec documents cross-module type resolution and using declarations for library types
- [x] **XMOD-06**: Cross-module resolution has integration tests covering type validation, method resolution, and error reporting

## Future Requirements

### Default Contract Methods

- **DEF-01**: Contract declarations support optional method bodies as default implementations
- **DEF-02**: Implementors can omit methods that have defaults; runtime falls back to default body
- **DEF-03**: `Iterable<T>.contains(item: T) -> bool` provided as a default method

### Array Specialization

- **SPEC-01**: Explicit `impl` blocks can specialize behavior for array types (e.g., optimized `contains` on `T[]`)

## Out of Scope

| Feature | Reason |
|---------|--------|
| Default contract method implementations | Significant cross-cutting feature; deferred to v15.0 with dedicated todo |
| `contains` on Iterable | Depends on default contract methods; deferred to v15.0 |
| `contains` on arrays | Removed in v14.0; will return via Iterable default impl or explicit specialization |
| Array `sort` | Requires non-trivial algorithm in Writ + `T: Ord` bound; defer to future |
| Lazy iterator chains | Requires coroutine or closure-based approach; ship eager methods first |

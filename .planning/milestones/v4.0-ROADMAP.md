## Phase Details

### Phase 47: Spec Amendments
**Goal**: The language specification accurately describes the struct/class split — `struct` as value type, `class` as reference type, `entity` as specialized class — across all affected sections
**Depends on**: Phase 46 (design record finalized)
**Requirements**: SPEC-01, SPEC-02, SPEC-03, SPEC-04, SPEC-05, SPEC-06, SPEC-07, SPEC-08, SPEC-09, SPEC-10, SPEC-11
**Success Criteria** (what must be TRUE):
  1. Section 8 states `struct` is a value type and `class` is a reference type with the `class` keyword present in the grammar
  2. The memory model table (§2.9.1) shows Structs as Value and includes a Classes row as Reference
  3. Construction semantics (§2.11) document that `new` behaves differently depending on whether the type is a struct (inline) or class (heap)
  4. The IL type system and module format sections (§2.15, §2.16.5) reflect value-struct register semantics and kind=4 for class TypeDefs
  5. Appendix B decision log records the struct/class split outcome
**Plans:** 4/4 plans complete

Plans:
- [ ] 47-01-PLAN.md — Rewrite Section 8 Structs, create Section 9 Classes, update EBNF grammar
- [ ] 47-02-PLAN.md — Update IL foundation sections (memory model, construction model, type system, module format)
- [ ] 47-03-PLAN.md — Update IL instruction sections (MOV, NEW, BOX/UNBOX) and Appendix B decision log
- [ ] 47-04-PLAN.md — Renumber files, fix heading prefixes, update TOC and cross-references

### Phase 48: IL Format
**Goal**: The module binary format correctly encodes and decodes class TypeDefs (kind=4) and carries format_version=3, making new modules distinguishable from v2 modules
**Depends on**: Phase 47
**Requirements**: IL-01, IL-02, IL-03
**Success Criteria** (what must be TRUE):
  1. A module written with kind=4 TypeDef entries round-trips through the reader/writer without data loss
  2. Modules report format_version=3 in their header
  3. A kind=0 (struct) module and a kind=4 (class) module both parse without errors, and the reader exposes the kind field to callers
**Plans:** 2/2 plans complete

Plans:
- [ ] 48-01-PLAN.md — Add Class=4 to TypeDefKind, bump format_version to 3, reader validation, builder API change
- [ ] 48-02-PLAN.md — Update assembler/disassembler, unify TypeDefKind across compiler and runtime

### Phase 49: VM Runtime
**Goal**: The VM executes struct and class values with the correct semantics — structs live inline in registers and copy on assignment, classes allocate on the heap and share references — and GC correctly traces both
**Depends on**: Phase 48
**Requirements**: VM-01, VM-02, VM-03, VM-04, VM-05, VM-06
**Success Criteria** (what must be TRUE):
  1. Assigning a struct value to a second register produces an independent copy — mutating the second does not affect the first
  2. `NEW` on a class (kind=4) allocates a heap object; `NEW` on a struct (kind=0) initializes the register inline without a heap allocation
  3. GC collection does not corrupt structs that contain embedded reference-type fields — the referenced objects are kept alive
  4. `BOX` on a value-struct register produces a heap-allocated boxed value usable as a generic argument; `UNBOX` recovers the struct value
  5. `MOV` of a value-struct register copies all fields (multi-word)
**Plans:** 2/2 plans complete

Plans:
- [ ] 49-01-PLAN.md — Add Value::InlineStruct variant, remove Copy derive, mechanical .clone() fixes across runtime
- [ ] 49-02-PLAN.md — NEW kind-dispatch, GET/SET_FIELD variant dispatch, GC InlineStruct tracing, tests

### Phase 50: Compiler Frontend
**Goal**: The compiler parses `class` declarations, generates correct inline initialization for value-struct construction, generates correct heap allocation for class construction, and rejects infinitely-sized recursive structs at compile time
**Depends on**: Phase 49
**Requirements**: COMP-01, COMP-02, COMP-03, COMP-04
**Success Criteria** (what must be TRUE):
  1. A Writ source file declaring `class Foo { ... }` parses without error and produces a class AST node distinct from a struct node
  2. `new SomeStruct { ... }` in a compiled module emits inline initialization IL (kind=0, no heap alloc instruction sequence)
  3. `new SomeClass { ... }` in a compiled module emits heap allocation IL (kind=4, matching current struct behavior)
  4. A struct that directly or transitively contains itself as a value-type field produces a compile error naming the cycle
**Plans:** 2/2 plans complete

Plans:
- [ ] 50-01-PLAN.md — class keyword through full frontend pipeline (lexer, CST, parser, AST, lowering, name resolution, type checking)
- [ ] 50-02-PLAN.md — class codegen (TypeDefKind::Class emission), recursive struct cycle detection

### Phase 51: Compiler Backend and Tests
**Goal**: The compiler emits correct structural equality for value-type structs, migrates closure capture environments to class kind, and all golden tests pass with format_version=3 and updated kind values. Entity kind stays unchanged (kind=2) per user decision.
**Depends on**: Phase 50
**Requirements**: COMP-05, COMP-06, COMP-07, TEST-01, TEST-02, TEST-03, TEST-04
**Success Criteria** (what must be TRUE):
  1. Two struct values with identical field contents compare equal using `==` without requiring a user-defined Eq impl
  2. ~~Entity declarations lower to kind=4 (class) TypeDefs~~ Entity declarations remain kind=2 per user decision (COMP-06 resolved, no code change)
  3. Closure capture environments emit as kind=4 (class) TypeDefs in emitted modules
  4. All existing golden tests pass after snapshot re-blessing with updated closure kind
  5. A recursive struct declaration (infinite-size cycle) produces a golden test that captures the expected compile error
**Plans:** 2/2 plans complete

Plans:

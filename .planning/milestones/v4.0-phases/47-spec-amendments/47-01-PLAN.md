**Rewrite `09_8_structs.md` for value-type semantics.** The file keeps its filename (renumbering happens in Plan 04). The heading stays `## 8. Structs` for now (prefix fix happens in Plan 04).

Rewrite section 8 with this structure:
- Opening paragraph: Structs are value types — named composite types with named fields, inline storage, copy-on-assign. They support methods and operator overloading via `impl` blocks.
- Keep the `Merchant` example but replace it with a `Vec2` example (value type is more natural for the opening). Show `new Vec2 { x: 1.0, y: 2.0 }`.
- **8.1 Construction**: Rewrite to describe inline/no-heap semantics. `new StructType { ... }` initializes the value inline — no heap allocation for the struct itself. Fields with defaults may be omitted. Keep the static method factory pattern example. Clarify that `new` for a struct does NOT allocate heap memory (contrast with classes in Section 9).
- **8.2 Shallow Copy Semantics**: Assignment copies all fields by value. Reference-typed fields copy the pointer — both copies share the same referenced object, but the struct values themselves are independent. Include the `Vec2` and `Note` examples from the former §8.4.3.
- **8.3 Structural Equality**: Value-type structs auto-derive field-by-field equality. Two structs are equal if and only if all corresponding fields compare equal. Reference equality for ref-typed fields. Classes require explicit `Eq` contract implementation (cross-ref to Section 9).
- **8.4 Passing Semantics**: Value-type structs are always passed by copy. `mut self` on a method mutates the local copy, not the caller's value. Same behavior as `int` and `float`.
- **8.5 Recursive Structs**: Recursive value-type structs are illegal (infinite size). Compiler error with the cycle named. Include the `Bad` and `Node` examples from the former §8.4.3. Suggest using `class` for recursive data structures.
- **8.6 Construction Sequence (IL)**: Rewrite to show the inline initialization IL. Since there is no heap allocation, `NEW` initializes the value in-place. Show the IL sequence for `new Vec2 { x: 1.0, y: 2.0 }`:
  ```
  NEW           r0, Vec2_type        // initialize value inline (no heap allocation)
  LOAD_FLOAT    r1, 1.0
  SET_FIELD     r0, x_field, r1
  LOAD_FLOAT    r1, 2.0
  SET_FIELD     r0, y_field, r1
  ```
  Note: No `CALL __on_create` step — value-type structs have no lifecycle hooks.

No version history notes, no "Changed in v4.0" callouts, no §8.4 design record. The spec reads as clean normative truth.

  <action>
Update the EBNF grammar in `28_27_grammar_summary_ebnf.md`:

1. Add `class_decl` as a separate EBNF production (not shared with struct_decl), positioned right after `struct_member`:
   ```ebnf
   class_decl     = 'class' IDENT [ generic_params ] '{'
                    { class_member } '}' ;
   class_member   = [ visibility ] property | on_decl ;
   ```
   Note: `class_member` includes `on_decl` (lifecycle hooks) which `struct_member` also has — but for structs, lifecycle hooks are now illegal, so `struct_member` should be updated to remove `on_decl`.

2. Update `struct_member` to remove lifecycle hooks:
   ```ebnf
   struct_member  = [ visibility ] property ;
   ```
   (Remove the `| on_decl` — value-type structs have no lifecycle hooks.)

3. Add `class_decl` to the `declaration` production list:
   ```ebnf
   declaration    = { attribute } [ visibility ] ( fn_decl | dlg_decl | struct_decl
                  | class_decl | enum_decl | contract_decl | impl_decl
                  | entity_decl | extern_decl
                  | const_decl | global_decl ) ;
   ```

4. Add `extern class_decl` alongside `extern struct_decl`:
   ```ebnf
   extern_decl    = 'extern' ( fn_sig ';' | struct_decl | class_decl
                  | component_decl ) ;
   ```

5. Update `new_expr` comment if it mentions structs only — it should note that `new` works for both structs (inline) and classes (heap).

## Phase Details

### Phase 52: Compiler and Runtime Preparation
**Goal**: The compiler and runtime have correct source position data and debug hooks so all subsequent LSP and DAP features are built on reliable foundations.
**Depends on**: Phase 51 (v4.0 complete)
**Requirements**: PREP-01, PREP-02, PREP-03, PREP-04, PREP-05
**Success Criteria** (what must be TRUE):
  1. `writ disasm` on any compiled .writil shows real 1-based line and column numbers (not zeroes or byte offsets) for every instruction's source location
  2. Saving a .writ file with a syntax error inside one function produces diagnostic output for that error; definitions in other functions remain available (partial AST from error recovery)
  3. `RuntimeHost` trait compiles with a `before_instruction(task_id, method_idx, pc) -> DebugAction` method and existing `NullHost`/`CliHost` are unaffected (default no-op)
  4. A `SuspendReason` enum distinguishes `Breakpoint`, `DebugStep`, and `HostRequest` suspensions so stepping over a `say()` call does not hang
  5. `writ disasm` shows local variable names and types alongside register indices in method bodies
**Plans**: 3 plans

Plans:
- [ ] 52-01-PLAN.md — DebugLocal type_ref extension, SourceSpan line numbers, disassembler .locals
- [ ] 52-02-PLAN.md — RuntimeHost debug hooks, DebugAction, SuspendReason
- [ ] 52-03-PLAN.md — Per-function error recovery in codegen pipeline

### Phase 53: LSP Server Skeleton and Diagnostics
**Goal**: Users see inline diagnostic squiggles in VS Code for Writ errors, and .writ files get syntax highlighting and language association immediately on installing the extension.
**Depends on**: Phase 52
**Requirements**: LSP-01, LSP-08, EXT-01, EXT-02
**Success Criteria** (what must be TRUE):
  1. Opening a .writ file in VS Code applies TextMate syntax highlighting (keywords, strings, numbers, dialogue blocks, entity names use distinct colors)
  2. VS Code activates the Writ language automatically when any .writ file is opened, without the user manually selecting a language mode
  3. After saving a .writ file with a type error, a red squiggle appears under the offending token within one second
  4. After fixing the error and saving, the squiggle disappears
  5. Opening any file in a writ.toml project shows diagnostics that reflect cross-file resolution (an error from a missing imported definition appears in the file that references it, not just the file that defines the gap)
**Plans**: 3 plans

Plans:
- [ ] 53-01-PLAN.md — writ-lsp crate, diagnostic conversion, AnalysisHost (standalone + project mode)
- [ ] 53-02-PLAN.md — VS Code extension skeleton, TextMate grammar, language configuration
- [ ] 53-03-PLAN.md — tower-lsp Backend wiring, main.rs entry point, diagnostic publishing

### Phase 54: LSP Navigation and Completions
**Goal**: Users can navigate their Writ codebase by hovering, jumping to definitions, finding references, and getting completions — all backed by the full type-checked AST.
**Depends on**: Phase 53
**Requirements**: LSP-02, LSP-03, LSP-04, LSP-05, LSP-06, LSP-07, DIFF-01, DIFF-02
**Success Criteria** (what must be TRUE):
  1. Hovering any identifier shows its type or signature in a tooltip (e.g., hovering a variable shows its inferred type; hovering a function call shows its parameter list and return type)
  2. Go-to-definition on any identifier jumps to its declaration — including definitions in other files in the same writ.toml project
  3. Find all references returns every use-site of a definition across all files in the project
  4. Typing `.` after a struct, class, or entity-typed expression shows a completion list of its fields, methods, and (for entities) extern component types
  5. Calling a function shows signature help with the active parameter highlighted as the cursor moves through arguments
  6. Semantic highlighting visually distinguishes entity names, component types, dialogue speaker identifiers, and keywords from each other (not just from generic identifiers)
**Plans**: 4 plans

Plans:
- [ ] 54-01-PLAN.md — Extend typecheck to return TypeEnv, add display_named, create queries.rs, analysis cache, ServerCapabilities
- [ ] 54-02-PLAN.md — Hover, go-to-definition, find-all-references handlers
- [ ] 54-03-PLAN.md — Completions (identifier + dot) and signature help handlers
- [ ] 54-04-PLAN.md — Semantic token highlighting and VS Code extension token scope mapping

### Phase 55: DAP Server Core
**Goal**: Users can launch a Writ program in the VS Code debugger, set breakpoints on source lines, step through execution, and see a call stack with real source locations.
**Depends on**: Phase 52
**Requirements**: DAP-01, DAP-02, DAP-03, DAP-05
**Success Criteria** (what must be TRUE):
  1. Pressing F5 in VS Code with a Writ launch.json configuration starts the program in the debugger without requiring any extra tool installation
  2. A breakpoint set on a .writ file line causes execution to pause at that line; the editor highlights the paused line
  3. Step over advances to the next source line in the same function; step into descends into a called function; step out resumes until the current function returns — all at source level
  4. The call stack panel shows real function names and source file locations (not IL method indices or byte offsets) for every frame
**Plans**: 2 plans

Plans:
- [ ] 55-01-PLAN.md — writ-dap crate, DebugHost with stepping state machine, BreakpointTable, compile-on-launch, Runtime accessors
- [ ] 55-02-PLAN.md — DapServer with DAP command dispatch, call stack rendering, step commands, main.rs binary

### Phase 56: DAP Advanced Inspection
**Goal**: Users can inspect and query program state while paused — reading local variables, evaluating watch expressions, and seeing all running Writ tasks as separate debugger threads.
**Depends on**: Phase 55
**Requirements**: DAP-04, DAP-06, DAP-07
**Success Criteria** (what must be TRUE):
  1. When paused at a breakpoint, the Variables panel shows each local variable by name with its current value (not register indices)
  2. A watch expression entered in the Watch panel evaluates against the current stack frame and shows the result while paused
  3. The Threads panel shows one entry per active Writ cooperative task; switching to a task's thread shows its call stack
**Plans**: 2 plans

- [ ] 56-02-PLAN.md — Scopes, Variables, Evaluate, and multi-task Threads handlers in DapServer

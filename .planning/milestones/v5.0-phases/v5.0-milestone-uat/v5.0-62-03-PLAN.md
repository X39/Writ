**The bug:** `stmt_item` in the top-level `item` choice accepts any expression as a top-level item. `asd asd asd` parses as valid `Expr::Ident` statements. No diagnostic is emitted.

**Fix approach:** Add a validation wrapper around `stmt_item` that emits a diagnostic for expression-statements at the top level. This is better than removing `stmt_item` entirely because `stmt_item` also handles `let` bindings and other statement forms that might appear at top level (though they'd be unusual).

In writ-parser/src/parser.rs, around line 3218:

1. Change the `stmt_item` from:
   ```rust
   let stmt_item = stmt.map_with(|s, e| {
       (cst::Item::Stmt(s), e.span())
   });
   ```
   To a `validate` wrapper that emits an error for expression-statements:
   ```rust
   let stmt_item = stmt.validate(|s, _e, emitter| {
       // Only expression-statements are invalid at top level.
       // Let bindings, while unusual at top level, are at least syntactically intentional.
       match &s {
           cst::Stmt::Expr { .. } => {
               emitter.emit(Rich::custom(
                   _e.span(),
                   "expression statements are not allowed at the top level; expected a declaration (fn, struct, entity, enum, etc.)",
               ));
           }
           _ => {}
       }
       s
   }).map_with(|s, e| {
       (cst::Item::Stmt(s), e.span())
   });
   ```

   Check which Stmt variants exist in the CST. Look at `cst::Stmt` enum — likely has `Expr`, `Let`, `Return`, `While`, `For`, etc. The key ones to reject at top level are `Expr` (bare expressions like `asd asd`). `Let` at top level is also wrong but less urgent; if it exists, reject it too:
   ```rust
   match &s {
       cst::Stmt::Expr { .. } | cst::Stmt::Return { .. } | cst::Stmt::Break { .. } | cst::Stmt::Continue { .. } => {
           emitter.emit(Rich::custom(
               _e.span(),
               "statement not allowed at the top level; expected a declaration (fn, struct, entity, enum, etc.)",
           ));
       }
       _ => {}
   }
   ```

   The `validate` method is from chumsky — it calls the closure with the parsed value and an error emitter, and the closure can emit errors while still returning the parsed value (allowing recovery to continue).

2. Verify the import: `Rich` should already be imported via chumsky prelude. Check top-of-file imports. If `validate` is not on the parser trait, use `.try_map` instead:
   ```rust
   let stmt_item = stmt.try_map_with(|s, e| {
       match &s {
           cst::Stmt::Expr { .. } => {
               Err(Rich::custom(e.span(), "expression statements are not allowed at the top level; expected a declaration"))
           }
           _ => Ok(s)
       }
   }).map_with(|s, e| {
       (cst::Item::Stmt(s), e.span())
   });
   ```
   But this might prevent recovery. Use `validate` if available (chumsky 0.9+ has it).

   If neither `validate` nor `try_map_with` is available, use `map_with` and emit via the extra's `emit` method if available. Check chumsky version in Cargo.toml. With chumsky 1.0-alpha, the approach would be different.

   Alternative simpler approach if chumsky APIs are tricky: Filter out `Stmt::Expr` entirely with `.filter`:
   ```rust
   let stmt_item = stmt
       .filter(|s| !matches!(s, cst::Stmt::Expr { .. }))
       .map_with(|s, e| {
           (cst::Item::Stmt(s), e.span())
       });
   ```
   This prevents bare expressions from being accepted, causing the parser to fail and emit an "expected declaration" error via chumsky's error recovery. This is the simplest approach.

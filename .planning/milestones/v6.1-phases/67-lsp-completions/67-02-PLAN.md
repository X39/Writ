RESEARCH FINDINGS on the bug:
1. `find_in_expr` uses `offset >= span.end` (half-open). For receiver `p` at span [N, N+1),
   `dot_offset - 1 = N = span.start`, which IS within [N, N+1). So single-char works.
2. FileId(0) is correct for standalone re-analysis.
3. The modified source preserves all byte offsets BEFORE the dot (receiver spans unchanged).
4. Most likely failure: receiver expression gets `TyKind::Error` in re-analyzed source,
   causing `build_dot_completions` to return empty via `_ => {}` arm.
5. Alternative failure: `expr_at_offset` returns `None` because the re-analysis fails
   to produce a typed AST for the modified source.

   fn test_expr_at_offset_receiver_for_dot_completion() {
       let src = "pub struct Point { x: int, y: int }\nfn main() { let p: Point = new Point { x: 1, y: 2 }; p }";
       let ast = build_typed_ast(src);
       // The final "p" in the source -- find it after "; "

       let expr = expr_at_offset(&ast, p_offset, FileId(0));

       let original = "pub struct Point { x: int, y: int }\nfn main() { let p: Point = new Point { x: 1, y: 2 }; p. }";

**Phase B: Fix based on diagnosis**

The diagnostic tests will reveal which step fails. Apply the appropriate fix:

- **If `expr_at_offset` returns `None`**: The half-open check `offset >= span.end` may be too strict. Check the actual span values in the debug output. The fix would be to adjust the condition to `offset > span.end` (closed interval) or ensure the offset calculation is correct. Research indicates the math should work, so also check if the modified source re-analysis places the `p` expression differently (e.g., as a statement expression rather than a tail expression, which might change how `find_in_expr` traverses).

- **If `expr_at_offset` returns an expression but `receiver_ty` is `TyKind::Error`**: The re-analyzed modified source has a type error for the receiver. This likely means removing the dot causes the last expression in the block to not type-check against the function's return type (if the function has return type annotation and `p` alone doesn't match). The fix: modify the source more carefully -- strip the dot AND any trailing characters up to the next `}` or `;`, replacing them with a matching-type expression, OR accept that dot-completions should work even with type errors by handling `TyKind::Error` receivers with a heuristic (look up the variable's declared type instead of the expression type).

- **If the analysis itself fails** (no typed_ast): The modified source has a parse error. Check what the modified source looks like -- `format!("{}{}", &original[..dot_pos], &original[dot_pos + 1..])` might create invalid syntax like `p }` which should parse as a block with tail expression. If it fails, the fix is to replace the dot with a space instead of removing it: `format!("{} {}", &original[..dot_pos], &original[dot_pos + 1..])`.

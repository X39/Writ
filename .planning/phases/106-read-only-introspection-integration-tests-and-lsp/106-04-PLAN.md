Create a golden .writ source file that demonstrates the static-vs-dynamic typeof distinction:

`refl_typeof_subtype.writ`:
```writ
contract Animal {
    fn speak() -> string;
}

struct Dog {
    name: string,
}

impl Animal for Dog {
    fn speak() -> string {
        "woof"
    }
}

fn main() {
    let static_type = typeof(Animal);
    let dog = Dog { name: "Rex" };
    let dynamic_type = typeof(Dog);
}
```

Key verification: The blessed .writil must show:
1. A TYPEOF instruction in `main` targeting the Animal contract TypeDef token (static typeof path)
2. A TYPEOF instruction in `main` targeting the Dog struct TypeDef token (dynamic typeof — while we use typeof(Dog) here as proxy since get_type() call resolution may not be available, the critical point is that the two TYPEOF tokens are DIFFERENT)
3. In the auto-generated `Dog::get_type` body, another TYPEOF targeting the Dog struct TypeDef token

The test proves: if a variable is declared as `animal: Animal` but holds a Dog, the compiler would emit TYPEOF with Animal's token for `typeof(animal)` (static declared type) and dispatch `animal.get_type()` to Dog's auto-generated body which uses TYPEOF with Dog's token (dynamic runtime type). The golden test locks this IL shape.

NOTE: If the compiler does not yet support `impl ContractName for StructName` syntax or if `typeof(ContractName)` fails, try alternative approaches:
- If `typeof(Animal)` fails on a contract, it means DefKind::Contract is not handled in the TypeOf Ident resolution. Fix by adding Contract to the match in check_expr/mod.rs (same pattern as the existing Struct/Class/Entity/Enum arms).
- If `impl Animal for Dog` fails, simplify to just `contract Animal { fn speak() -> string; }` and `struct Dog { name: string }` with separate typeof calls on each — this still proves different TYPEOF tokens.

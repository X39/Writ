## Summary

Phase 114 fixes two distinct bugs in the `writ-dap` crate. Both are self-contained within the DAP layer and the compiler's dialogue lowering pipeline.

**DAP-01** is a source attribution regression: `build_stack_frames` in `writ-dap/src/server/inspection.rs` always uses `self.source_paths.first()` for the `source` field of every stack frame. This was a known compromise documented in a comment: "True per-frame source file attribution requires FileId in SourceSpan (not available in current module format -- deferred to future phase)." The module format already carries the data needed — `DefEntry` in the resolver has `file_id: FileId`, and all named method bodies are keyed by `DefId` via `EmittedBody.method_def_id`. The fix maps `method_idx -> FileId` and uses it in `build_stack_frames`.

**DAP-02** is a dialogue interpolation crash or incorrect output: the `lower_dlg_text` function in `dialogue.rs` already delegates to `lower_fmt_string`, and `lower_fmt_string` already handles `StringSegment::Expr` nodes. However, the golden fixture `dlg_fn_mix.writ` explicitly sidesteps interpolation with the comment "No string interpolation in text lines (avoids .into<string>() on string type)." This indicates there is a known failure when `{name}` interpolation appears inside dialogue text lines. The fix requires diagnosing the specific failure (likely a type-check or emit path for the `into<string>()` call generated by `lower_fmt_string` when the inner expression is a string type), adding a new dialogue golden fixture, and adding a DAP integration test that runs a dialogue with interpolation.

**Primary recommendation:** Fix `build_stack_frames` to look up `FileId` from a pre-built `method_idx -> source_path` map (constructed from `source_paths` and `DefMap`), and add a new golden fixture that exercises `{name}` interpolation in a dialogue text line.

## Root Cause Analysis (Both Bugs)

### DAP-01: Source Attribution

**Location:** `writ-dap/src/server/inspection.rs` — `build_stack_frames` method (lines 457-552)

**Current code:**
```rust
// Use the first source file path as fallback for all frames.
// True per-frame source file attribution requires FileId in SourceSpan
// (not available in current module format -- deferred to future phase).
let source_path = self.source_paths.first()
    .map(|(_, p)| p.as_str())
    .unwrap_or("");
```
This assigns the entry file's path to every frame, regardless of which file the method is defined in.

**What data is available:** The `DapServer` already holds `source_paths: Vec<(writ_diagnostics::FileId, String)>` mapping FileId to filesystem path. The resolver's `DefMap` knows each function's `file_id`. The `EmittedBody` carries `method_def_id: Option<DefId>`. What's missing is a runtime-accessible `method_idx -> FileId` mapping.

**Feasible fix path:** During serialization in `serialize.rs`, the method bodies are written in MethodDef order. The `def_token_map` maps `DefId -> MetadataToken`, and `MetadataToken::row_index()` gives the MethodDef row (1-based). The inverse — MethodDef index to FileId — can be built by iterating `bodies` in `emit_bodies`. This creates a `Vec<Option<FileId>>` indexed by method_idx that the DAP server can load.

**Simplest fix (no module format change):** Build the `method_idx -> FileId` map inside `DapServer` at launch time by iterating `module.method_defs` indices and matching through `source_paths`. The challenge is that after serialization, `EmittedBody.method_def_id` (a `DefId`) is no longer directly accessible — only the final `Module` is present.

**Alternative fix (module format change):** Add `file_id: u32` to `SourceSpan` — each span carries its own file. This is the most correct but requires format version bump, writer/reader changes, and compiler changes to populate it.

**Pragmatic fix (no format change required):** The `DapServer` already stores `source_paths: Vec<(FileId, String)>`. During launch, after compilation, the compiler's `emit_bodies` pipeline can return a separate `Vec<Option<FileId>>` indexed by method_idx. This can be threaded through `compile_and_load` and stored on `DapServer`. This avoids any module format changes.

**Even simpler approach:** Store a `method_file_ids: Vec<Option<FileId>>` returned from `run_pipeline`/`compile_and_load_project`. The compiler already knows, when emitting each body, which `file_id` that `DefId` came from via `DefMap`. The compile-time `DefMap` is the authoritative source.

The simplest implementation that avoids module format changes: thread `Vec<Option<writ_diagnostics::FileId>>` (one entry per method_def, parallel to `method_defs`) from `run_pipeline` through `compile_and_load_project`/`compile_and_load` to `DapServer`, then use it in `build_stack_frames` to pick the right source path from `self.source_paths`.

To build this map: during `emit_bodies` in `serialize.rs`, after the `method_def_body_indices` loop, a parallel `method_def_file_ids: Vec<Option<FileId>>` can be built by looking up each body's `method_def_id` in the `def_token_map`-linked `DefMap`. However, `serialize.rs` doesn't currently hold a `DefMap` reference.

**Cleanest approach that fits existing architecture:** Access the DefMap that was used during name resolution. The `run_pipeline` function in `launch.rs` discards it after type-checking. Capture and return it, or build the `method_idx -> FileId` map inside `run_pipeline` and return it alongside the compiled bytes.

Looking at what the compiler resolution step produces:
```rust
let (resolved, resolve_diags) = writ_compiler::resolve::resolve(&asts_refs, &path_refs);
```

The `resolved` value contains `TypedAst` after type-checking but the per-file source assignment of functions is already embedded in the ASTs via `(FileId, &Ast)` tuples. The simplest in-compiler approach: after type-checking, iterate `asts_refs` and `typed_ast` to build the map before calling `emit_bodies`.

**Recommended approach:** Add a helper in `launch.rs` that builds `Vec<Option<FileId>>` by iterating `per_file_asts: Vec<(FileId, Ast)>` — each top-level `fn`/`dlg` declaration in file N maps to FileId N. Match by method order as they'll be emitted. Return this alongside the compiled module bytes.

Actually the most direct path: extend `emit_bodies` (or its output) to also return `Vec<Option<FileId>>` indexed by method_def order. The serialization loop in `serialize.rs` already iterates `method_def_body_indices` in MethodDef order and has access to `body.method_def_id` (a `DefId`). The `DefMap` carries `file_id` per `DefEntry`. Pass the `DefMap` into `serialize` (it's currently not passed) and build the map there.

But `serialize.rs`'s `serialize_bodies` function signature is already complex. The simplest non-format-change path given the current code structure:

1. In `launch.rs::run_pipeline`, after resolving, collect `per_file_asts` as `Vec<(FileId, Ast)>`. Walk the ASTs to build a `fn_name -> FileId` map.
2. After compiling and loading the module, iterate `module.method_defs` to read method names, look them up in the map, and produce `Vec<Option<FileId>>`.
3. Return it from `run_pipeline` and thread through `compile_and_load_project`.
4. Store as `method_file_ids: Vec<Option<FileId>>` on `DapServer`.
5. In `build_stack_frames`, look up `method_file_ids.get(method_idx)` to select the right entry from `self.source_paths`.

Name-based matching is fragile (overloads). Better: pass `def_map` or file-mapping through the compiler pipeline. However, looking at the actual codebase, the `resolve::resolve()` API returns a `resolved` struct that the type-checker consumes. The DefMap is internal to `resolve`.

**Final recommended approach for DAP-01:** Extend the compile pipeline to return `Vec<Option<FileId>>` (indexed by MethodDef order) alongside the compiled bytes. Build it in `run_pipeline` by instrumenting the body collection phase. Since `EmittedBody.method_def_id` is a `DefId` and `DefEntry.file_id` is available via `def_map`, pass the needed data through. The public compiler API (`emit_bodies`) can return an extra `method_file_ids: Vec<Option<FileId>>` in addition to the binary bytes.

### DAP-02: Dialogue String Interpolation

**Location:** `writ-compiler/src/lower/dialogue.rs` — `lower_dlg_text` function (line 535)

**Current path works correctly in principle:** `lower_dlg_text` converts `DlgTextSegment::Expr` nodes to `StringSegment::Expr` and delegates to `lower_fmt_string`, which wraps each expression with `.into<string>()`. The type-checker handles this correctly for `int`, `float`, `bool`, and `string` types (routes through `into_string` builtins).

**Known issue:** `dlg_fn_mix.writ` explicitly sidesteps dialogue interpolation. The comment "avoids .into<string>() on string type" suggests the codegen or type-check for string-typed interpolation in a dialogue context was known to fail or crash.

**Specific failure scenario:** A dialogue text line like `@npc Hello {name}!` where `name: string` produces an `into_string` call on a string receiver. In `builtins.rs`, the `string -> string` path returns `Some(r_src)` (a no-op), which is correct. The `.into<string>()` on a string should work.

**However,** the comment in `dlg_fn_mix.writ` hints at something different: not a crash but rather incorrect behavior. The dialogue text `{name}` in the raw text is parsed by `split_dlg_text_segments`, which produces `DlgTextSegment::Expr`. The inner expression goes through `lower_expr`, which produces a typed expression. When this expression has type `string`, the `lower_fmt_string` wraps it in `GenericCall { field: "into", type_args: [string] }`. The type-checker at `check_expr/call.rs:493+` recognizes this pattern and normalizes to `into_string`. The emitter at `builtins.rs:129` handles `string::into_string` as a no-op.

**The actual DAP-02 issue is more likely:** the runtime executing a dialogue function with interpolation may crash inside `say()` because the string heap reference from `I2S`/string concatenation is not properly handled, OR the issue is that a dialogue fixture with interpolation doesn't exist yet for the DAP integration test to compile and run.

**What the success criteria says:** "A dialogue text line containing `$"Hello {name}!"` interpolation executes through lower_fmt_string and produces the correct output string." The `$"..."` syntax here is a formattable string used INSIDE dialogue text via a code escape or directly in a text line. This could mean:
- `@npc $"Hello {name}!"` — a dialogue speaker line where the text contains a `$"..."` formattable string
- OR that `lower_dlg_text` fails when text contains `{expr}` interpolation

The `split_dlg_text_segments` function handles `{expr}` interpolation in raw dialogue text (not `$"..."` syntax). The `$"..."` formattable string syntax would be a code escape: `$ say(speaker, $"Hello {name}!")`. But success criterion 3 says "dialogue text line containing `$"Hello {name}!"` interpolation" — this is a regular `@npc Hello {name}!` text line where the text contains a brace-interpolated expression.

**Most likely actual bug:** There is no existing test fixture that exercises dialogue text with `{expr}` interpolation (dlg_fn_mix.writ explicitly avoids it). Creating a fixture and running it through the compiler/DAP pipeline will reveal the actual failure mode. The fix is either:
a) A compiler bug in `lower_dlg_text` when `DlgTextSegment::Expr` contains a string-typed expression (the `.into<string>()` on a string should be a no-op, but may have a codegen edge case)
b) A missing golden test fixture + DAP integration test

**Research conclusion:** The `lower_dlg_text` → `lower_fmt_string` pipeline is structurally correct. The bug is most likely that no integration path exercises this code in the DAP context. Creating a test fixture `writ-golden/tests/golden/dlg_interp.writ` with `@speaker Hello {name}!` and running it through the DAP will either pass (bug was just untested) or reveal the actual crash point.

## Architecture Patterns

### DAP-01 Fix Architecture

**Pattern: Method-to-File mapping at launch time**

```
compile_and_load_project() -> (Module, Vec<(FileId, String)>, Vec<Option<FileId>>)
                                        ^source_paths          ^method_file_ids
```

The `method_file_ids` vector is indexed by `method_idx` (parallel to `module.method_defs`). Each entry is `Some(file_id)` for named methods from a source file, `None` for synthetic methods (lambdas, built-in impls).

In `build_stack_frames`:
```rust
// Instead of:
let source_path = self.source_paths.first().map(|(_, p)| p.as_str()).unwrap_or("");

// Use:
let frame_file_id = self.method_file_ids
    .get(method_idx)
    .and_then(|opt| *opt);
let (source_path, filename) = frame_file_id
    .and_then(|fid| self.source_paths.iter().find(|(id, _)| *id == fid))
    .map(|(_, p)| {
        let name = std::path::Path::new(p).file_name()
            .and_then(|n| n.to_str())
            .unwrap_or(p.as_str());
        (p.as_str(), name)
    })
    .unwrap_or_else(|| {
        let fallback = self.source_paths.first().map(|(_, p)| p.as_str()).unwrap_or("");
        let name = std::path::Path::new(fallback).file_name()
            .and_then(|n| n.to_str())
            .unwrap_or(fallback);
        (fallback, name)
    });
```

**Building `method_file_ids` in `run_pipeline`:**

After resolving, the `per_file_asts` variable holds `Vec<(FileId, Ast)>`. After type-checking, the `typed_ast` has been processed. After calling `emit_bodies`, the compiler returns the binary bytes. The method_def order matches the order in which functions are collected — same order as `per_file_asts` walks.

However, the most reliable approach is to use the public `writ_compiler::resolve` API which returns a struct carrying `DefMap`. If `DefMap` is not exposed, an alternative is to build the map inside `run_pipeline` by walking `per_file_asts`: collect all `fn`/`dlg` declarations per `FileId`, and match them against `module.method_defs` by name after compilation.

**Simplest build path (post-compilation, name-based):**
```rust
// After Module is built from bytes:
let mut method_file_ids: Vec<Option<FileId>> = vec![None; module.method_defs.len()];
for (file_id, ast) in &per_file_asts {
    for decl in &ast.decls {
        let fn_name = decl_name(decl); // extract name from AstDecl
        if let Some(idx) = find_method_idx_by_name(&module, fn_name) {
            method_file_ids[idx] = Some(*file_id);
        }
    }
}
```

This works for single-method-per-name cases. For overloaded functions it may assign the wrong FileId, but all overloads of the same name will be in the same file (enforced by the compiler), so this is safe.

## Common Pitfalls

### Pitfall 1: Reversing method_file_ids construction scope
**What goes wrong:** Building `method_file_ids` only for project-mode and forgetting single-file mode.
**Why it happens:** `compile_and_load` (single-file) and `compile_and_load_project` (project) are separate code paths in `launch.rs`.
**How to avoid:** Add `method_file_ids` construction to both paths. Single-file always has `FileId(0)` for all methods — use `vec![Some(FileId(0)); module.method_defs.len()]`.
**Warning signs:** Stack frames show correct file for project-mode but wrong file for single-file launch.

### Pitfall 2: Off-by-one in method_idx vs method_defs index
**What goes wrong:** `method_file_ids[method_idx]` panics or returns wrong entry because method_idx from `call_stack_frames` is 0-based but `module.method_defs` is also 0-based — they should align.
**Why it happens:** The `call_stack_frames` API returns `(method_idx, pc)` pairs. `method_idx` is the 0-based index into `module.method_defs`. The `method_file_ids` vector must be in the same order.
**How to avoid:** Build `method_file_ids` with `vec![None; module.method_defs.len()]` and index it with `method_idx` directly.
**Warning signs:** Files show as `None` for all frames despite correct source_paths.

### Pitfall 3: Dialogue interpolation test fixture uses wrong syntax
**What goes wrong:** Test fixture uses `$"Hello {name}!"` (formattable string syntax) inside dialogue text instead of `{name}` (dialogue inline interpolation syntax).
**Why it happens:** The two syntaxes look similar but are parsed differently. `@speaker $"Hello {name}!"` would try to parse `$` as a DlgLine sigil (code escape) rather than inline interpolation. Inline interpolation is `@speaker Hello {name}!`.
**How to avoid:** Use `{name}` (no `$` prefix) in dialogue text lines for inline interpolation. Use `$"..."` only inside code escapes (`$ ...`).
**Warning signs:** Parse errors or the fixture not exercising `lower_dlg_text` at all.

### Pitfall 4: Forgetting the single-file DapServer source_paths initialization
**What goes wrong:** After DAP-01 fix, single-file mode still shows wrong file because `compile_and_load` returns a `(Module, &str)` not `(Module, Vec<(FileId, String)>)`.
**Why it happens:** `handle_launch` in `handlers.rs:151` has a special code path for single-file mode that only stores `vec![(FileId(0), program_path.clone())]`.
**How to avoid:** The fix is additive — `method_file_ids` in single-file mode is always `vec![Some(FileId(0)); module.method_defs.len()]`, which correctly resolves all frames to the single source file.
**Warning signs:** Single-file mode continues to report first-file for all frames regardless of DAP-01 fix.

### Pitfall 5: Dialogue text Expr nodes with complex expressions
**What goes wrong:** A dialogue text line like `@npc Score: {player.score + bonus}` causes a panic in `lower_fmt_string` because the inner expression is not handled.
**Why it happens:** `lower_fmt_string` calls `lower_expr` recursively on the inner expression. `lower_expr` should handle any valid expression, but if the type-checker does not recognize the result type for `.into<string>()`, it falls through to an error path.
**How to avoid:** Start with a simple identifier interpolation (`{name}` where `name: string`) as the test case. Complex expressions can be deferred.
**Warning signs:** Compiler error "no method `into<string>` on type X" for the interpolated expression type.

```rust
fn lower_dlg_text(
    segments: Vec<Spanned<DlgTextSegment<'_>>>,
    outer_span: SimpleSpan,
    ctx: &mut LoweringContext,
) -> AstExpr {
    let string_segments: Vec<Spanned<StringSegment<'_>>> = segments
        .into_iter()
        .map(|(seg, span)| {
            let converted = match seg {
                DlgTextSegment::Text(s) => StringSegment::Text(s),
                DlgTextSegment::Expr(e) => StringSegment::Expr(e),
            };
            (converted, span)
        })
        .collect();
    lower_fmt_string(string_segments, outer_span, false, ctx)
}
```

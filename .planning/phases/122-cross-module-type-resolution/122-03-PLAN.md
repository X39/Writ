**1. [dependencies] Section**

Document the new `[dependencies]` table in `writ.toml`:

```toml
[dependencies]
writ-std = "path/to/writ-std.writc"
```

Or the detailed form:
```toml
[dependencies]
writ-std = { path = "path/to/writ-std.writc" }
```

Explain:
- Each entry names a pre-compiled `.writc` module that the compiler will load at compile time
- Paths are relative to the project root (where `writ.toml` lives)
- The dependency must be a valid `.writc` binary module (compiled with `writ build`)
- The dependency's public types, functions, and contracts become available in user source files

**2. Cross-Module Type Resolution**

Document the semantics:
- When the compiler encounters a type name (e.g., `List<int>`) that is not defined in the current compilation unit, it checks type definitions loaded from dependency modules
- Library types are visible at the top level -- no `using` declaration is required if the type has no namespace, or the namespace matches
- If the library type lives in a namespace (e.g., `collections::List`), the user must either use the fully-qualified name or add a `using` declaration:
  ```writ
  using collections;
  let list: List<int> = List::new();
  ```
- Library types participate in the same name resolution rules as locally-defined types
- If a user file defines a type with the same fully-qualified name as a library type, the compiler reports a "duplicate definition" error naming the library module

**3. Virtual Module Types**

Document that the Writ runtime provides a built-in virtual module containing:
- Standard contracts: `Add`, `Sub`, `Mul`, `Div`, `Mod`, `Neg`, `Not`, `Eq`, `Ord`, `Index`, `IndexSet`, `BitAnd`, `BitOr`, `Iterable`, `Iterator`, `Into`, `Error`, `Hashable`, `Reflectable`
- Built-in types: `Option<T>`, `Result<T, E>`, `ChoiceOption`
- These are available in every compilation unit without explicit dependency declaration
- These types follow the same resolution mechanism as user library types

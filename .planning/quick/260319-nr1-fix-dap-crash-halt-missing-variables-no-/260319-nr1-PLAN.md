<objective>
Fix DAP crash halt variable inspection: when a Writ program crashes (e.g., unwrap on None),
VSCode halts with stack frames visible but NO variables shown. The root cause is threefold:
1. `CrashInfo::StackFrame` does not preserve register values -- they are lost during unwind
2. `resolve_task_id` uses `all_task_ids()` which excludes Cancelled tasks, so scopes/variables
   handlers silently return empty
3. `count_active_locals` and `get_variables` have no fallback path for crash state

Purpose: Enable developers to inspect local variable values at the point of a runtime crash.
Output: Working variable inspection during crash halts, validated by integration test.
</objective>

**Step 3 -- Make DAP inspection crash-aware** (`writ-dap/src/server/inspection.rs`):

The core issue: `resolve_task_id` uses `all_task_ids()` which excludes Cancelled tasks.
Three methods need crash-state fallback: `count_active_locals`, `get_variables`, and
`do_evaluate`. Rather than fixing `resolve_task_id` (which is used elsewhere and semantically
correct), add a crash-aware resolution path.

3a. Add a private helper method to DapServer that checks if the stored `self.task_id` matches
the requested thread_id and has crash info:

```rust
/// Resolve a thread_id to a TaskId, including crashed (Cancelled) tasks.
/// Falls back to self.task_id if the task is crashed and matches.
fn resolve_task_id_or_crashed(&self, thread_id: i64) -> Option<TaskId> {
    // First try active tasks
    if let Some(id) = self.resolve_task_id(thread_id) {
        return Some(id);
    }
    // Fallback: check if self.task_id matches and has crash_info
    if let Some(task_id) = self.task_id {
        if task_id.index as i64 == thread_id {
            if let Some(rt) = self.runtime.as_ref() {
                if rt.crash_info(task_id).is_some() {
                    return Some(task_id);
                }
            }
        }
    }
    None
}
```

3b. Update `count_active_locals` to use `resolve_task_id_or_crashed` and fall back to
crash info when `call_stack_frames` returns None or empty. When using crash frames:
- Crash frames are already in top-to-bottom (display) order, so `display_frame_idx`
  indexes directly (no reversal needed)
- Use the crash frame's `pc` (instruction-index) converted via `instr_to_byte_pc`
- Count debug_locals whose range includes that byte_pc

3c. Update `get_variables` to use `resolve_task_id_or_crashed` and fall back to crash
info when `call_stack_frames` returns None or empty. When using crash frames:
- Index into `crash.stack_trace[display_frame_idx]`
- Use the crash frame's stored `registers` as the register slice
- Use crash frame's `pc` converted to byte_pc via `instr_to_byte_pc`
- Call `collect_frame_variables(module, method_idx, byte_pc, &crash_frame.registers, heap)`

3d. Similarly update `do_evaluate` to work with crash state using the same pattern.

Important: The `build_stack_frames` method already handles crash fallback (it reads
CrashInfo.stack_trace when call_stack is empty). The frame IDs it generates use
display_frame_idx directly (enumerate in display order), so the display_frame_idx values
from scopes/variables will correctly index into crash frames.

<objective>
Investigate and fix why `benchmark/cases/fib/fib.writ` (fib(40)) appears to never exit when compiled and run with `writ run`.

Root cause (already diagnosed): The Writ VM is approximately 50-75x slower than Lua for compute-intensive recursive workloads. fib(30) takes 1.6s, fib(35) takes 23s, so fib(40) would take ~750s (~12 minutes). It IS completing eventually, but appears to "never exit" because it's extremely slow.

The primary bottlenecks are:
1. `body[pc].clone()` in execute_one — clones every instruction on every dispatch
2. Per-instruction overhead: bounds checking, byte_pc lookup via Vec indexing, ExecContext construction
3. `Value::clone()` in register access throughout arith/calls handlers (Value has heap-allocated variants)
4. Match dispatch overhead on 91-variant enum

Purpose: Make the VM fast enough that fib(40) completes in reasonable time (target: under 2 minutes, matching ~Python speed)
Output: Optimized VM dispatch loop and value representation
</objective>

<task type="auto">
  <name>Task 1: Eliminate instruction cloning and reduce per-instruction overhead</name>
  <files>
    writ-runtime/src/dispatch/mod.rs
    writ-module/src/instruction.rs
  </files>
  <action>
The single biggest win: stop cloning instructions on every dispatch.

1. In `execute_one()` (dispatch/mod.rs line 288), change `let instr = body[pc].clone();` to borrow instead: `let instr = &body[pc];`. This requires changing the match to match on `&Instruction::...` variants. Since we increment `frame.pc` on line 289 before the match, the borrow from `body` (which borrows from `modules`) should not conflict with the mutable borrows in the match arms because `frame` is re-borrowed via `ctx.task` which is a separate mutable borrow path.

However, there's a borrow conflict: `frame` is obtained from `task.call_stack.last_mut()` which borrows `task`, and `body` borrows `modules`. These should be independent borrows. The issue is that `frame.pc += 1` happens while we still hold `frame`. We need to:
- Read the instruction index (pc) as a local variable (already done on line 229)
- Drop the frame borrow after incrementing pc
- Get the instruction reference from body[pc] using the saved pc value
- Then proceed with dispatch

Specifically refactor the hot path to:
```rust
let method_idx = task.call_stack.last().unwrap().method_idx;
let pc = task.call_stack.last().unwrap().pc;
// bounds checks...
let body = &modules[current_module_idx].decoded_bodies[method_idx];
let instr = &body[pc];
// Now increment PC
task.call_stack.last_mut().unwrap().pc = pc + 1;
task.instructions_executed += 1;
// Build ExecContext and dispatch
```

This avoids cloning the instruction enum entirely. For the `Switch { offsets }` variant which contains a `Vec<i32>`, this saves a heap allocation per switch instruction execution.

2. For the `Instruction` enum in writ-module/src/instruction.rs: add `#[derive(Copy)]` where possible. The `Switch` variant contains `Vec<i32>` which prevents Copy. Consider changing `Switch { r_tag: u16, offsets: Vec<i32> }` to use a `Box<[i32]>` or `Arc<[i32]>` — but this is lower priority since the borrow approach above avoids the clone entirely.

Actually, since we're borrowing, we don't need Copy at all. Just ensure the borrow approach works.

3. Move the `byte_pc` lookup and debug hook OUTSIDE the critical path when debug is not enabled. Currently every instruction does:
```rust
let byte_pc = module.byte_offsets.get(method_idx).and_then(|offsets| offsets.get(pc)).copied().unwrap_or(0);
if host.debug_enabled() { ... }
```
Wrap the entire byte_pc computation inside the `if host.debug_enabled()` block since byte_pc is only used for debug. This eliminates a Vec lookup per instruction in non-debug mode.

4. Remove the intermediate `ExecContext` struct allocation from the hot path. Instead of constructing ExecContext on every instruction, pass the individual parameters directly to the most common dispatch functions (arith ops, branches). Keep ExecContext only for complex operations (calls, objects, entities). This reduces struct construction overhead.

Actually — ExecContext is stack-allocated and the compiler should optimize it. The bigger win is #1 and #3. Focus on those and leave ExecContext as-is if refactoring it is too invasive.

CRITICAL: After making changes, ensure ALL match arms in the dispatch handle borrowed instructions correctly (use `ref` bindings for any owned data like the Switch offsets Vec).

<task type="auto">
  <name>Task 2: Optimize Value representation for Copy semantics on the hot path</name>
  <files>

  <action>
Read writ-runtime/src/value.rs to understand the current Value enum layout. The fib benchmark only uses `Value::Int` — the main overhead is cloning Value when it could be copied.

Key optimizations for the fib hot path:

1. If Value currently derives Clone but not Copy (likely due to String/Vec/Ref variants), add helper methods for the common case:
   - `fn as_int(&self) -> Option<i64>` (returns by value, no clone)
   - `fn is_int_val(&self, v: i64) -> bool`

2. In the arithmetic dispatch functions (arith.rs), replace patterns like:
   ```rust
   let a = frame.registers[r_a as usize].clone();
   let b = frame.registers[r_b as usize].clone();
   match (a, b) { (Value::Int(x), Value::Int(y)) => ... }
   ```
   With borrow-based patterns:
   ```rust
   match (&frame.registers[r_a as usize], &frame.registers[r_b as usize]) {
       (Value::Int(x), Value::Int(y)) => {
           frame.registers[r_dst as usize] = Value::Int(x + y);
       }
       ...
   }
   ```
   This avoids cloning values just to destructure them. For int/float/bool operations, borrowing is sufficient since the inner values are Copy types.

3. In calls.rs `exec_call`, the argument collection loop clones each argument:
   ```rust
   args.push(caller.registers[r_base as usize + i].clone());
   ```
   For the common case of int/float/bool args, this clone is unnecessary overhead. Consider:
   - If all args are scalar (no Ref/InlineStruct), do a direct register copy
   - Or just keep the clone here since function calls are less frequent than arith ops

4. In the comparison functions (CmpLtI, CmpEqI), ensure they borrow rather than clone, since they only need to read the integer values.

Focus the optimization effort on the instructions that appear in the fib inner loop:
- LoadInt (load constant 1)
- CmpLtI or CmpEqI (n <= 1)
- BrTrue/BrFalse (conditional)
- SubI (n-1, n-2)
- Call (recursive call)
- AddI (fib(n-1) + fib(n-2))
- Ret (return value)

These ~7 instruction types account for 99%+ of execution in fib. Each should be as lean as possible: borrow registers, no allocation, no unnecessary branching.
